# Proposal delivery and adjacent workflow assessment — 24 October 2026

This is a targeted source, regression, browser and deployment review, not an independent penetration test or proof that every defect has been eliminated. No customer proposal, customer mailbox, paid generation, customer email, payment or production migration was used.

## Confirmed defects and fixes

| Finding | Impact | Correction and evidence |
| --- | --- | --- |
| User reports `TenderCrestBid AI Autonomous Engine` in delivered proposal | Incorrect service attribution in email; carried into the new Word attachment | The current repository has no hard-coded occurrence of that old name. The relay passes the incoming generated message into all formats. Normalize this exact known service-brand typo, including case variants, in subject and message before rendering. Test checks subject, plain text, HTML and valid DOCX; unrelated names and factual statements remain intact. Existing emails and stored Airtable text are not retroactively edited. |
| HTTP-success response with no provider message ID was accepted as successful delivery | False positive when provider response is incomplete/malformed | Proposal relay and contact notification now require a nonempty string message ID. Tests cover missing, empty and incorrectly typed IDs. Acceptance is still distinct from inbox delivery. |
| Proposal send timeout/malformed response had only a generic failure | Caller could mistake an ambiguous send for a safe resend | Post-dispatch exceptions and missing IDs report `deliveryState: uncertain` with instructions to verify before retrying. There is no automatic retry. This does not establish durable duplicate prevention in the upstream automation. |
| JSON accepts lone Unicode surrogates and XML-forbidden characters | Draft can fail to open/render as valid Word XML | Reject these inputs before sending while preserving valid accented text, CJK and emoji. Existing input-size and rendering limits remain; no silent truncation. |
| Relay accepted non-text/encoded HTTP bodies and lax mailbox syntax | Inconsistent handling, provider rejection, possible address-list ambiguity | Explicit HTTP-body validation, byte ceiling, single-mailbox syntax, length and control-character checks. No additional recipients are accepted. |
| Contact handler accessed properties on JSON null | Unhandled request failure | Reject null, primitives, arrays and encoded payloads before accessing fields; test proves no provider call. |
| Contact name/mailbox controls and address-list syntax were accepted | Header/provider errors and ambiguous reply/acknowledgment recipient | Reject controls and list/display-name syntax; preserve one plain mailbox. Tests cover injection and malformed recipient inputs. |
| Contact provider and lead-storage requests had no timeout | A slow provider could stall contact intake | Add bounded request timeouts. Keep lead/acknowledgment failure best-effort after accepted primary notification, so the form does not invite duplicate submissions. |
| Contact errors logged arbitrary exception messages; lead object had a duplicate `Follow-up Due` key | Possible content in logs; redundant configuration hiding intended fields | Generic failure logs, no provider/customer exception text; single follow-up field. Tests verify accepted-notice/failed-storage/failed-ack behavior and no leaked exception content. |

## Workflow review and checks

- **Account, uploads and submission:** reviewed verified-account/delivery-email binding, owner/private source checks, source hashes, supported MIME/size rules, durable submission identity, trial/credit reservation and uncertain queue handling. Existing mocked regression tests exercise denial and retry paths without a real generation or credit charge. No new billing or access-rule change was required.
- **Generation and external automation:** current code queues the original Airtable schema. Generation prompts and email sign-off are managed outside this repository. No current Airtable administration connector is available, so the exact source prompt/script producing the old name was not inspected or edited. The delivery-boundary fix protects future messages sent through this relay, but the upstream stored draft may retain the old text. A delivery path bypassing this relay is outside that protection.
- **Proposal status:** ownership-filtered authenticated lookup fetches status only. `Ready for Review` occurs before email delivery; the page correctly says inbox receipt is unconfirmed. No false sent/delivered state was added.
- **Email and Word:** safe text/HTML rendering, shared content, real tables/headings, Unicode, draft markings, bounded structures, valid Office archive/XML, sender/reply-to behavior, failures and authentication are covered. Previously validated fictional Word rendering in LibreOffice remains applicable; current changes add explicit brand/Unicode/acceptance cases.
- **Knowledge/compliance:** reran 12 offline Knowledge Base browser scenarios and 17 offline compliance browser checks. They cover role isolation, citations/untrusted markup, approvals/edit invalidation, source review, CSV/XLSX downloads, keyboard/mobile behavior, sign-out and proposal handoff without submission. All external calls are intercepted.
- **Project proposal exports:** reviewed private artifact authorization, source integrity checks, evidence/revision checks, final approval and package expiration. Existing workspace/export and cross-member tests remain in the full regression suite. A fresh real hosted multi-role run or natural-expiry test was not repeated for these email/contact-only changes.
- **Public site and billing:** searched tracked source for old product naming. Existing build/configuration tests check source exclusion and production wiring; Stripe/webhook and credit tests remain in regression coverage. No checkout, pricing, feature flags, reminder activation or payment action is changed.
- **Dependencies:** `npm audit --omit=dev` returned zero known vulnerabilities at the time of this review. This is registry evidence, not a guarantee against undisclosed vulnerabilities.

## Remaining operational gaps

1. **Clean the upstream brand source.** Inspect the deployed Airtable AI instructions and final email script, replacing the old sign-off with `TenderCrest AI Autonomous Engine`. Runtime correction is implemented; source-prompt correction is not claimed.
2. **Delivery events.** There is no per-proposal delivered/bounced event reflected in the proposal status page. A signed provider webhook, durable message-to-submission mapping and retention policy would be needed for trustworthy tracking; a send-only provider key cannot prove inbox receipt.
3. **Duplicate email prevention.** The unchanged legacy automation payload has no stable delivery-event identity. It cannot reliably distinguish a retry from a deliberately new identical proposal. Do not deduplicate solely by content hash. Durable event IDs and coordinated automation/provider idempotency require an upstream change; uncertain sends should be investigated before replay.
4. **Mailbox compatibility.** HTML is structurally safe and previously checked at mobile/desktop widths; Outlook/Gmail inbox rendering and real Word-attachment delivery have not been exercised in this review. No customer email was sent.
5. **Archiving and assurance.** The relay generates Word in memory, not a permanent document archive. Existing workspace ZIP retention remains separate. Independent certifications, contractual recovery objectives, provider retention agreements, all-scope Netlify secrets and distributed contact-abuse protection are not resolved by these code fixes. Previously accepted release limitations remain unchanged.

No unsupported claim of complete end-to-end production delivery, independent security certification or zero remaining bugs should be inferred from these checks.
